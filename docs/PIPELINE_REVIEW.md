## 1. Последовательность действий в коде

Точка входа — `main.py` → `pipeline/run.py: run(args)`. Шаги идут по порядку, каждый сохраняет
результат в `outputs/main/` и может быть запущен отдельно (`--steps`).

| № | Шаг | Что происходит | Где |
|---|---|---|---|
| 0 | аргументы | `build_main_parser()`: пути, параметры всех шагов; `set_cameras(--cameras)`; `main.py` проверяет наличие данных и весов (если весов нет, а детекции на диске есть — `detect` пропускается) | `main.py`, `run.py` |
| 1 | `detect` | `YoloDetector.detect_video()` по каждому видео; на кадр берётся объект класса `truck` с максимальной уверенностью; из маски — площадь и центроид (точка для триангуляции), контур; флаги `edge_clipped` (рамка у края кадра), `too_small`, `unreliable` (= край, мала или conf < 0.5). Результат `detections/cam{N}.csv`, `cam{N}_polygons.npz`, `meta.json`. Повторный запуск пропускает готовые камеры (`--redetect`) | `pipeline/detect.py`, `detection/yolo.py`, `detection/schema.py` |
| 2 | загрузка | `load_detections()` → `{камера: {кадр: Detection}}` | `pipeline/detect.py` |
| 3 | `center` (офлайн, базовый) | `run_evaluation()`: CSV цели с NaN в испорченных ячейках (`load_target`); сплайн по цели только для направления движения; **скан смещения кадров** −3…+3 (ошибка после вычитания постоянного смещения в осях грузовика); `triangulate_frames()` → `triangulate_robust()` на каждом кадре (ближайшая точка к лучам, число обусловленности, перебор «без одной камеры», пока все ошибки перепроецирования ≤ 20 px); 2D-статистика по камерам; P-сплайн по точкам триангуляции (узлы 15 кадров, вес = число камер, Хьюбер 1 м); кинематика; графики `center/plots`, `center/report.md`. Возвращает сплайн и 3D-точки | `pipeline/center.py`, `reconstruction/triangulation.py`, `bspline.py` |
| 4 | `optimize` (офлайн) | контрольные точки сплайна центра маски подгоняются по пикселям всех камер: `least_squares(trf, huber, jac_sparsity)` с остатками «проекция − пиксель»·√conf, штрафом за глубину и регуляризацией по ускорению/рывку (λ = 10/100, единицы см и кадры) | `reconstruction/objective.py`, `optimizer.py`, `regularization.py` |
| 5 | `cab` (офлайн) | `BoxObservations.from_detections()` (рёбра рамок x1 x2 y1 y2 + «ребро не у края»); начальная траектория — центр маски, сдвинутый на L/2 вперёд и H/2 вниз; `fit_cab_trajectory()` подбирает контрольные точки и габариты коробки так, чтобы рамка проекции совпала с рамками детектора; точка — низ передней грани, из неё — центр кабины | `reconstruction/cab_model.py` |
| 6 | `realtime` (**основной**) | `TruckModel.from_fbx()` (оболочка, точка CSV, центр кабины, масштаб ×3.186; без FBX — коробка); `run_tracker()` вызывает `CabTracker.step()` на каждом кадре по порядку: (а) учёт, какая камера «появилась»; (б) инициализация: триангуляция центров масок ≥2 надёжных камер, 8 кадров, скорость из МНК; (в) прогноз «постоянная скорость», шум процесса вдоль/поперёк курса; (г) прогнозная рамка = проекция выпуклой оболочки модели; `detect_occluded_edges()` — ребро ушло внутрь при совпадающем противоположном → закрыто; (д) итерированное обновление EKF по рёбрам (5 итераций Гаусса–Ньютона, Хьюбер, вес по уверенности и по «только что появилась»); (е) пределы: Δv ≤ 12/8 м/с² вдоль/поперёк, сдвиг ≤ 1.5 м; (ж) выход: точка CSV, центр кабины, скорость, курс (= направление скорости), СКО, статус `initializing/measured/partial/predicted` | `reconstruction/visibility.py`, `truck_model.py`, `fbx_reader.py` |
| 7 | `approx` (**новый**, базовый) | «обычная аппроксимация» 3D-точек триангуляции без модели объекта: причинный полином по окну прошлых кадров (реальное время; без точек — прогноз по прямой) и один полином по всем точкам (офлайн) | `reconstruction/approximation.py` |
| 8 | `compare` | `evaluate_methods()`: для каждого варианта ошибка относительно CSV цели (медиана/p95/RMSE/макс), MAE, **по осям X/Y/Z**, без постоянного смещения в осях грузовика, по числу камер, **по статусу кадра**, кинематика (скорость, скачки, путь), **калибровка погрешности** трекера (СКО фильтра против фактической ошибки); `plot_comparison()` — графики 01–09; `plot_camera_coverage()` — вид сверху с секторами и препятствиями; `write_report()` → `report.md`; `metrics.json`; `metrics_summary.csv`; `print_summary()` — сводка в консоль | `pipeline/run.py`, `pipeline/coverage.py` |
| 9 | `video` | на каждый кадр каждой камеры: рамка детектора, силуэт модели (или коробка), центр кабины, след за 90 кадров (только прошлое), метка CSV, статус и ошибка; кодирование ffmpeg. Нет файла видео — камера пропускается с предупреждением | `pipeline/run.py: render_videos` |

Зависимости между шагами: `center` нужен всегда (сплайн — начальное приближение `cab`, 3D-точки — вход
`approx`); `compare`/`video` требуют `optimize` и `cab` (считаются или берутся с диска).

## 2. Проверка реализации (что подтверждено)

- **Модель камеры.** `Camera.R = [right; −up; forward]`, проекция `u = cx + fx·x/z`, `v = cy + fy·y/z`
  совпадает с формулами задания; `pixel_to_ray` — обратное преобразование; тесты `test_camera.py`.
- **Триангуляция.** Ближайшая точка к лучам (сумма `I − dd^T`), проверка обусловленности,
  робастный перебор подмножеств — корректно и покрыто тестами.
- **B-сплайн.** P-сплайн со штрафом на вторые разности (не вырождается на участках без точек),
  IRLS-Хьюбер, производные через `BSpline.derivative` с обрезкой коэффициентов — верно.
- **Оптимизация по пикселям и коробка.** Единицы согласованы (см, кадры), структура якобиана
  проверена тестом на зависимость остатков от параметров, штраф за глубину — есть.
- **Трекер.** Уравнения итерированного EKF в информационной форме
  (`x_{i+1} = x⁻ + (P⁻¹ + HᵀR⁻¹H)⁻¹ Hᵀ R⁻¹ (z − h(x_i) + H(x_i − x⁻))`) — стандартные; шум процесса
  `G = [½I; I]` для dt = 1 кадр — верно; якобиан только по положению, скорость правится через
  кросс-ковариацию — верно для измерения положения; причинность доказана тестом (обрезанный ряд даёт те же
  оценки). Пошаговый и пакетный режимы совпадают.
- **Все 77 тестов проходят** (8 пропущены: нужны реальные данные/FBX).

### Замечания, оставленные как есть (предложения ниже)

- `NUM_VIDEO_FRAMES = 1001`, 1920×1080 и размер сенсора — константы; для другой сцены их надо выносить
  в параметры (число кадров — из видео или детекций).
- `step_realtime` меняет глобальный `METHOD_NAMES["realtime_ref"]` (косметика).
- После `_apply_limits` ковариация `P` не корректируется — фильтр считает, что принял полное обновление.
- В детекторе на кадр берётся один объект (максимальная уверенность) — ТЗ допускает несколько объектов.
- Инициализация требует 8 кадров с ≥2 надёжными центрами масок: на синтетике, где в начале грузовик
  надёжно видит одна камера, трекер молчал 112 кадров.
- На синтетике отношение «фактическая ошибка / СКО фильтра» ≈ 2.8, в пределах 2σ лишь 28 % кадров —
  **ковариация занижена** (в ней нет ошибки курса и несовпадения формы с рамками). На реальных данных
  надо посмотреть график `compare/09_realtime_uncertainty.png` после прогона.

до ~14 м на участке одной камеры — та же слабость, что и на реальных данных.

## 4. Соответствие ТЗ и предложения по повышению точности в реальном времени

| Пункт ТЗ | Сейчас | Пробел |
|---|---|---|
| 1. Детекция центра объекта на каждой камере | YOLO-seg, центроид маски; для трекера — рёбра рамки | детектор дообучен на тех же видео; один объект на кадр |
| 2. Многокамерная триангуляция | `triangulate_robust` (инициализация, базовые варианты); основной трекер — обобщение: совместное обновление по всем камерам через проекцию 3D-модели | участок с одной камерой: глубина не определена |
| 3. Фильтрация и сглаживание | EKF (реальное время), P-сплайн и least_squares (офлайн) | курс только из скорости |
| 4. Выбросы и пропуски | Хьюбер везде, перебор камер в триангуляции, закрытые рёбра, прогноз без детекций, пределы ускорения | ковариация занижена |
| 5. Рамка на контрольном видео, графики координат от времени | `videos/realtime_cam{N}.mp4`; графики 01–09, в т.ч. **07 координаты от времени** | — |
| 6. Оценка точности и погрешности | `report.md`, `metrics.json`, `metrics_summary.csv`, график 09 | честной отложенной оценки детектора нет |
| 7. Демонстрация, альтернативы | README, этот документ; варианты: центр маски, оптимизация по пикселям, коробка, модель, аппроксимация | — |
| Критерий «произвольное число камер» | `--cameras`, камеры читаются по номерам | число кадров и размер кадра — константы |

Предложения ниже упорядочены по ожидаемому выигрышу для реального времени; все причинные
(используют только кадры ≤ t), кроме G, где задержка указана явно.

**A. Измерение по силуэту маски, а не только по рамке** (ТЗ п.1–3; слабое место «медленный поворот
650–850»). Маски уже сохраняются (`cam{N}_polygons.npz`). В `CabTracker._measure` добавить остатки
«контур проекции оболочки модели ↔ контур маски» (расстояние до полигона в K точках контура или IoU
как скалярное измерение с численным якобианом). Кабина асимметрична, поэтому силуэт различает
«вперёд/назад», и курс можно вернуть в состояние (именно 180°-симметрия рамки ломала прежний EKF с
курсом). Ожидание: курс в повороте из формы, а не из шумной скорости; меньше бокового ухода точки кабины.

**B. Ограничение по рельефу дороги** (ТЗ п.2; слабое место «одна камера 200–300»). Высота Z почти
полностью задаётся дорогой: построить карту высот по офлайн-траектории (или из сцены Unreal) и
добавить псевдоизмерение `z = h(x, y)` с малым СКО. Это статическое знание сцены, а не будущие кадры,
поэтому реальное время не нарушается. Одна камера + известная высота + известный размер грузовика —
глубина становится наблюдаемой.

**C. СКО ребра по дальности и размеру рамки** (ТЗ п.2, п.4). Сейчас `edge_sigma_px = 20` для всех
камер и дистанций. Пиксельная ошибка рамки примерно пропорциональна размеру рамки, а её цена в метрах
растёт с дальностью: `σ_edge = a + b·size_px`, а также меньший вес камерам с узким полем зрения на
большой дальности. Подбирать по невязкам, а не по CSV цели.

**D. Калибровка ковариации** (ТЗ п.6). По графику 09 на реальных данных оценить отношение
ошибка/СКО; добавить в `R` член несовпадения модели с рамкой и перенести неопределённость курса в
точку вывода (`P_point = J P Jᵀ`, J — производная точки CSV по курсу). Тогда СКО в отчёте становится
честной погрешностью, которую требует ТЗ.

**E. Инициализация по одной камере.** Известны размеры грузовика → дальность из высоты/ширины рамки
(`Z ≈ f·H/h_px`), плюс рельеф (B). Снимет задержку старта, когда вначале грузовик видит одна камера.

**F. Модель движения для резких поворотов** (ТЗ п.3). Сейчас «постоянная скорость» с большим шумом
(6 м/с²). Вариант — IMM из двух моделей (постоянная скорость и постоянный поворот) или скорость
поворота в состоянии, когда появится измерение курса из A. Уменьшит запаздывание в повороте без роста
шума на прямых.

**G. Сглаживание с фиксированной задержкой (опционально).** Задержка 3–5 кадров (100–170 мс) и
RTS-сглаживание внутри окна дают заметно меньше скачков. Это по-прежнему онлайн-система, но с
объявленной задержкой; решение — за заказчиком (ранее заглядывание отклонено).

**H. Детектор** (ТЗ п.1, п.6). (1) Честная оценка: обучить на 3 камерах, проверить на 2 (сейчас
оценка на обучающих данных). (2) YOLO-pose с ключевой точкой «передний бампер»: разметку можно
получить автоматически проекцией точки модели по известным позам камер — тогда точка CSV измеряется
напрямую, а не через рамку. (3) Временная проверка: детекция, чья рамка далеко от прогноза трекера,
понижается в весе (сейчас частично через Хьюбер).

**I. Несколько объектов** (ТЗ: «один либо несколько объектов»). Детектор возвращает все кандидаты;
на каждый трек — прогнозная рамка на каждой камере; сопоставление по IoU (венгерский алгоритм);
рождение трека по триангуляции несопоставленных детекций ≥2 камер, смерть после N кадров `predicted`.
Трекер уже инкапсулирован в `CabTracker`, поэтому это надстройка `MultiTracker` над ним.

**J. Воспроизводимость и произвольная сцена** (критерий 3). Вынести число кадров, размер кадра,
сенсор, список камер и фокусы в конфиг сцены (`scene.json`); число кадров брать из видео. `--cameras`
уже есть.

**K. Инженерия реального времени.** Трекер — единицы мс на кадр; узкое место — YOLO на 5 потоках.
Детекция камер параллельно (по процессу на камеру), трекер по таймстампам кадров, обработка
пропущенных кадров как `predicted`. Замерить и записать в отчёт задержку «кадр → оценка».

**L. Сверка с Unreal.** Масштаб актора ×3.186 и положение опорной точки (сейчас откалиброваны по
