# Продакшен-архитектура потоковой системы

Дополняет `docs/ARCHITECTURE.md` (алгоритмы) — здесь то, что касается производительности,
режимов работы и надёжности. Код: `pipeline/streaming.py`, `pipeline/autotune.py`,
`detection/yolo.py`, `reconstruction/camera_scheduler.py`.

## Поток данных

```
CAPTURE (поток на камеру)      VideoSource / DetectionSource: ограниченная очередь (queue_size),
   │                           новый кадр вытесняет старый; live: переподключение источника
   ▼
SYNCHRONIZATION                Synchronizer: связка кадров одного момента (sync_tolerance_ms),
   │                           устаревшие кадры (max_frame_age_ms) отбрасываются
   ▼
CAMERA SCHEDULER               ACTIVE / PROBE / SLEEP; прогноз видимости по фильтру
   │
   ▼
INFERENCE                      YoloAdapter: пакет активных камер одним вызовом;
   │                           бюджет max_images_per_tick (лишние камеры — по кругу);
   │                           бэкенд torch / onnx / openvino (detection/yolo.py)
   ▼
TRACKER                        CabTracker: фильтр Калмана, рёбра рамки + 3D-модель;
   │                           dt по меткам времени; без детекций — прогноз (PREDICTED)
   ▼
SMOOTHING                      StreamingBSpline в фоновом потоке (SMOOTHED TRACK, лаг lag_frames)
   ▼
OUTPUT                         stream_track.csv, performance_report.json/md, видео (ffmpeg)
```

Причинность: на тике t используются только кадры с меткой ≤ t; REALTIME TRACK не заглядывает
вперёд. Бюджет изображений не нарушает причинность — он только решает, какие камеры
детектировать в этом тике.

## Режимы

| | LIVE | REPLAY (pacing) | REPLAY --no-pacing | DETECTIONS |
|---|---|---|---|---|
| источник | RTSP/устройства | видеофайлы в реальном темпе | видеофайлы | готовые CSV |
| приоритет | минимальная задержка | честная симуляция РВ | без потерь (все кадры) | алгоритмы/метрики |
| потери кадров | контролируемые (вытеснение старых) | как в live | нет (lossless-очередь) | нет |
| назначение | эксплуатация | испытания РВ | оценка качества | быстрые эксперименты |

Требования LIVE и REPLAY не смешиваются: lossless-очередь включается только при
`--no-pacing` (файл ждёт потребителя), в live/pacing очередь вытесняющая и задержка
ограничена `queue_size`, `max_frame_age_ms` и бюджетом изображений.

## Бэкенды детектора

`detector.backend`: `torch` | `onnx` | `openvino` | `auto`.

- Экспорт в ONNX/OpenVINO выполняется один раз и кэшируется рядом с весами
  (`models/best.onnx`, `models/best_openvino_model/`); dynamic shapes — один файл на все imgsz.
- `auto`: при CUDA/MPS — torch; на CPU — бэкенд из `configs/performance_profile.json`
  (если профиль есть и пакет установлен), иначе torch. Никаких молчаливых сюрпризов:
  выбранный бэкенд пишется в лог и в `meta.json` детекций.
- `detector.retina_masks=false` заменяет маску полного разрешения на центроид по полигону
  контура (формула шнурования) — постобработка в разы дешевле, контур тот же.

## Бюджет изображений и планировщик

На слабом CPU детекция всех активных камер каждый тик невозможна. Два механизма:

1. `CameraScheduler` (был раньше): ACTIVE / PROBE / SLEEP, прогноз видимости, гистерезис.
2. `streaming.max_images_per_tick` (новое): жёсткий верхний предел изображений на тик.
   Лишние активные камеры обходятся по кругу (давно не детектированные — первыми);
   камера, срезанная бюджетом, в этом тике «не наблюдалась» (не считается промахом).
   Минимум бюджета — 2: фильтру нужны две камеры в одном тике для инициализации и стерео.

## Автонастройка (pipeline/autotune.py)

- `--auto-tune`: замер доступных бэкендов × размеров на реальных весах (секунды),
  выбор самого быстрого с imgsz ≥ `--min-imgsz` (по умолчанию 640 — качество),
  расчёт бюджета из фактической скорости, сохранение `configs/performance_profile.json`.
- `--auto-config`: применение сохранённого профиля; несовпадение железа (модель CPU,
  ядра, CUDA) — предупреждение с советом перекалибровать.
- Ручные `--set раздел.ключ=значение` применяются ПОСЛЕ профиля и всегда сильнее.

## Надёжность

- Live-источник пропал → переподключение каждые 2 с (до 30 попыток), камера не теряется
  навсегда; трекер в это время работает по остальным камерам.
- Ctrl+C → корректное завершение: источники останавливаются, сплайн-поток закрывается,
  результаты и отчёт производительности пишутся на диск.
- Все очереди ограничены (`queue_size`), бесконтрольного роста задержки нет.
- Пустые детекции, кадры без камер, камера без строки позы (live) — штатные ветки, не исключения.
- Отчёт `performance_report.json` пишется каждым прогоном: тики/с, изображения YOLO/с,
  задержка p50/p95/max, вытесненные кадры, состояния планировщика, max RSS.

## Ограничения текущего оборудования

См. `docs/HARDWARE_PROFILE.md` и `docs/PERFORMANCE_REPORT.md`: на CPU AMD Ryzen 5 4500U
полная обработка 5 × 30 = 150 изображений/с недостижима ни одним бэкендом; система работает
в адаптивном режиме (бюджет 2 изобр./тик, ~9 изобр./с на OpenVINO@640) с честным прогнозом
между детекциями.
