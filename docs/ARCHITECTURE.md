# Архитектура потоковой системы мультикамерного 3D-трекинга

Документ описывает модернизированную систему (ветка `claude/lucid-davinci-vuf745`): что из прежнего
проекта переиспользовано, какие компоненты добавлены, какая математика внутри и как всё связано.
Команды запуска — в README (раздел «Потоковая система»), результаты — `docs/FINAL_REPORT.md`.

## 2. Поток данных на одном тике

```
источники кадров (поток на камеру, очередь ≤ queue_size, старое вытесняется)
      │  Frame(camera, index, timestamp, image, captured_at)
      ▼
Synchronizer: связка кадров с |t − t_ref| ≤ sync_tolerance; устаревшие (> max_frame_age) отброшены;
              камера вне допуска исключена из тика (причина пишется в stream_track.csv)
      ▼
CameraScheduler.plan(): по состоянию фильтра — вероятность видимости сейчас и через horizon,
              состояния ACTIVE / PROBE / SLEEP, принудительные проверки → какие камеры детектировать
      ▼
Detector.detect(кадры выбранных камер): YOLO пакетно (или готовые детекции) → рамка, центроид маски, флаги
      ▼
CabTracker.step(index, камеры, детекции, dt):
      прогноз F(dt), Q(dt) → прогнозная рамка силуэта модели на каждой камере → закрытые рёбра →
      fusion.build_point_measurement(): центроиды − поправка ракурса → триангуляция, ковариация, гейт NIS →
      итерированное обновление (рёбра + 3D-точка, Хьюбер, корреляция) → пределы ускорения → курс →
      REALTIME TRACK: X Y Z, V, |a|, курс, ковариация, статус, камеры, NIS, репроекция
      ▼
StreamingBSpline.add/update (фоновый поток): окно window_frames, IRLS-Хьюбер, λ_a, λ_j →
      SMOOTHED TRACK на now − lag (своя метка времени), замороженная история
      ▼
StreamRecorder: stream_track.csv, smoothed_track.csv, performance_report.{json,md}, видео с наложением, графики
```

Причинность: на тике t все входы имеют метки ≤ t. SMOOTHED TRACK отстаёт на `lag_frames` и помечен
кадром, к которому относится; он не подменяет REALTIME TRACK.

## 3. Адаптивный выбор камер (`camera_scheduler.py`)

**Вероятность видимости.** Состояние фильтра даёт центр `c`, скорость `v`, ковариацию `P` и курс.
Сигма-точки положения: `c` и `c ± k·σ_i·e_i` по трём главным осям `P` (k = `sigma_scale`), всего 7;
для горизонта `h` кадров — `c + v·h`, ковариация увеличена на `(0.1·h)²·vvᵀ`. Для каждой сигма-точки
силуэт модели (оболочка FBX или 8 углов коробки) проецируется в камеру; доля точек силуэта перед
камерой и внутри кадра с запасом `margin_px`, усреднённая по сигма-точкам, — `p_now` (h = 0) и
`p_horizon` (h = `horizon_frames`). Доля точек у края кадра (`border_px`) — признак «объект уходит».

**Состояния и переходы** (с гистерезисом `hysteresis_frames` для «понижающих» переходов):

| из | в | условие |
|---|---|---|
| ACTIVE | PROBE | `p_now < active_threshold` N кадров подряд, либо объект геометрически виден, но не найден `occluded_patience_frames` кадров (препятствие) |
| PROBE | ACTIVE | детекция в PROBE (сразу), либо `p_now ≥ active_threshold` и недавно найден |
| PROBE | SLEEP | `p_horizon < probe_threshold` N кадров подряд |
| SLEEP | PROBE | `p_horizon ≥ probe_threshold` (сразу) |

Детекция: ACTIVE — каждый кадр; PROBE — раз в `probe_period_frames` (3 FPS при 30); SLEEP — раз в
`sleep_period_frames` контрольная проверка (0 — никогда).

**Принудительная проверка** всех кандидатов (`p_horizon ≥ probe_threshold`): СКО положения >
`force_std_m`; NIS 3D-точки > `force_nis`; ошибка репроекции > `force_reproj_px`; нет измерений на
активных камерах (`frames_since_measurement > 0` или `cameras_used = 0`); объект у края кадра активной камеры.

**Геометрическое качество.** `q = (100 / дальность, м) · (1 + max sin ∠(луч, лучи активных камер))`:
ближняя камера даёт больше пикселей на метр, камера с большим углом к остальным — лучше глубину.
Добор до `min_active` и обрезка до `max_active` — по `p_now · q`; камеры, которые «видят, но не находят»,
в добор не попадают.

Выход на тик: `CameraPlan` (кого детектировать, состояния, `p_now`, `p_horizon`, качество, причины);
статистика: доля детекций от захваченных кадров, среднее число активных камер, принудительные тики.

## 4. Триангуляция реального времени и согласование точек (`fusion.py`)

**Геометрия.** `triangulate_robust` (ближайшая точка к лучам: `Σ(I − d_i d_iᵀ) X = Σ(I − d_i d_iᵀ) C_i`,
перебор подмножеств, пока все ошибки перепроецирования ≤ `max_reproj_px`). Дополнительные проверки:
точка перед всеми камерами-инлаерами; максимальный угол между лучами ≥ `min_ray_angle_deg` (иначе
глубина не определена — измерение не выдаётся); СКО точки ≤ `max_point_std_m`.

**Ковариация точки.** Якобиан проекции камеры i в точке X (координаты камеры x, y, z; строки R — r₁..r₃):

    J_i = (1/z) · [ f_x (r₁ − (x/z) r₃) ; f_y (r₂ − (y/z) r₃) ]      (2×3)
    Σ_X = ( Σ_i J_iᵀ J_i / σ_px² )⁻¹ · covariance_inflation

σ_px — ожидаемое СКО центроида на изображении (8 px по умолчанию); `covariance_inflation` — запас на
несовпадение центроида с точкой модели.

**Согласование физических точек** (режим `model_corrected`). Центроид маски на разных ракурсах — разные
точки кузова. По прогнозу фильтра (центр `c⁻`, курс) для каждой камеры считаются проекция центра
модели `π(c⁻)` и центроид площади выпуклой оболочки проекции силуэта `g`. Поправка ракурса
`δ = g − π(c⁻)`; исправленный пиксель `u' = u_маски − δ` относится к центру модели. Триангуляция `u'`
даёт точку, согласованную между камерами и с состоянием фильтра. Ошибка поправки (из-за ошибки
прогноза и несовпадения формы) учитывается в ковариации. Ключевые точки не придумываются: без модели
(или в режиме `centroid`) используется сырой центроид, и это честно хуже (вариант B).

**Что сравнивается** (`pipeline/variants.py`): A — только рёбра; B — сырые центроиды; C —
согласованная точка + рёбра; D — + сплайн; E — + планировщик. Совместная оптимизация положения
модели по всем камерам с априорной оценкой — это и есть итерированное обновление фильтра
(раздел 5): MAP-задача `min ‖x − x⁻‖²_{P⁻¹} + Σ‖z_k − h_k(x)‖²_{R_k⁻¹}` решается Гауссом–Ньютоном,
где `h` — рёбра рамки силуэта и 3D-точка. Последовательное обновление (точка, потом рёбра) заменено
одновременным — так корреляция и веса учитываются в одной системе.

## 5. Фильтр Калмана (`visibility.py`)

**Состояние.** CV: `[x y z vx vy vz]` (ед. мира, ед./кадр); CA: `+ [ax ay az]`. Переход и шум для
произвольного dt (в кадрах, из меток времени `dt = (t − t_prev)·fps`):

    CV: F = [[I, dt·I],[0, I]],  Q = G Q_a Gᵀ, G = [dt²/2·I; dt·I],  Q_a = R_h diag(σ_∥², σ_⊥², σ_z²) R_hᵀ
    CA: F = [[I, dt·I, dt²/2·I],[0, I, dt·I],[0, 0, I]],  Q = G Q_j Gᵀ, G = [dt³/6; dt²/2; dt]

`R_h` — оси «вдоль / поперёк курса / вверх»: шум ускорения задаётся по осям грузовика.

**Измерения.** (1) Рёбра x₁ x₂ y₁ y₂ рамки проекции силуэта модели на каждой камере (численный
якобиан по положению; рёбра у края кадра и закрытые препятствием исключены; вес по уверенности и
«только что появилась»). (2) 3D-точка из `fusion` с ковариацией `Σ_X` (H = [I 0 0]). Гейт: NIS
`rᵀ(P⁻ + Σ_X)⁻¹ r ≤ point_gate_nis` (χ²₃, 16 ≈ 99.9 %). Корреляция: центроид и рамка одной камеры
получены из одной маски → `R` рёбер этой камеры умножается на `edge_inflation_with_point`.

**Обновление** — итерированный EKF в информационной форме (Гаусс–Ньютон по MAP):

    Λ = P⁻⁻¹ + Σ_k H_kᵀ R_k⁻¹ H_k,   g = Σ_k H_kᵀ R_k⁻¹ (z_k − h_k(x_i) + H_k (x_i − x⁻))
    x_{i+1} = x⁻ + Λ⁻¹ g,   P⁺ = Λ⁻¹

Хьюбер: `R_k ← R_k · max(1, |r_k| / (√S_k · k_H))`. После обновления — физические пределы:
изменение скорости за dt не больше `max_longitudinal_mps2 / max_lateral_mps2`, сдвиг положения не
больше `max_correction_per_frame`, ускорение (CA) ограничено по модулю.

**Гейт детекций** (ложные рамки, другой объект). Пока трек подтверждался ≥2 камерами (рёбра двух
камер или принятая 3D-точка) не позже `gate_max_age` кадров назад и СКО < `gate_max_std_m`, рамка с
IoU к прогнозной < `gate_iou` и центром дальше `gate_distance` размеров прогнозной рамки отбрасывается
(`rejected_cameras` в выходе; планировщику такая камера считается «не нашла»). Две защиты от
«запирания» на ложной гипотезе: одна камера (в том числе ложная) подтверждением не считается, поэтому
без второй камеры гейт через `gate_max_age` кадров выключается; и гейт никогда не отбрасывает
большинство детекций тика — если с прогнозом не согласно большинство, неправ прогноз.

**Контроль расходимости.** Если `reinit_after_bad_frames` кадров подряд триангуляция ≥2 камер не
проходит гейт NIS (или ≥2 рамки отброшены), трек считается ушедшим: по стереоточкам этих кадров
состояние переинициализируется (робастная подгонка прямой по буферу, выбросы отбрасываются). Это
единственный способ быстро вернуться после плохой инициализации: пределы ускорения, нужные для
плавности, иначе растягивают возврат на десятки кадров.

**Инициализация.** Основная — триангуляция центроидов ≥2 камер за `init_frames` кадров (скорость из
МНК по точкам). Если за всё окно стереоточек не было — инициализация по одной камере: дальность из
высоты рамки и известной высоты модели (с поправкой на наклон камеры), большая начальная ковариация,
трек помечен неподтверждённым (гейт выключен, пределы скорости ослаблены ×3) до первого подтверждения
двумя камерами. На синтетике ошибка такого старта — десятки метров (одна камера не даёт глубины); без
неё в сценарии «одна камера» оценки не было бы вовсе.

**Курс** — отдельная переменная с динамикой: цель — направление сглаженной скорости (EMA), изменение
за кадр не больше `min(heading_rate_limit_dps, v / min_turn_radius_m)` — ограничение Аккермана: при
малой скорости курс почти не меняется, и шум направления медленной скорости не раскачивает ориентацию;
при скорости ниже `heading_min_speed_mps` курс держится. Это убирает
дребезг курса на медленных участках и при остановке, но курс по-прежнему выводится из движения:
рамка одинакова при повороте модели на 180°, поэтому измерять ориентацию по рамке нельзя (прежний
EKF с курсом в состоянии «переворачивал» грузовик). Честная ориентация требует измерения по силуэту
маски (следующий шаг, маски уже сохраняются).

**Выход на тик** (`FrameEstimate`): положение центра и точки вывода, `velocity_mps`, `speed_mps`,
`acceleration_mps2` (CA — из состояния; CV — сглаженная разность скоростей), курс, `covariance`
(3×3), `position_std`, число камер с детекцией / давших рёбра / в точке, `point_nis`, `reproj_px`
(средняя невязка рёбер после обновления), `status` (`initializing / measured / partial / predicted`),
`quality` (`point+edges / point / edges / partial / predicted`).

## 6. Скользящий B-сплайн (`streaming_bspline.py`)

Задача на окне `[now − window, now]` по измерениям `p_i` (центр из фильтра) с весами `w_i = 1/σ_i²`:

    min_c Σ_i w_i ρ_H(‖B(t_i) c − p_i‖) + λ_a ∫‖P''‖² dt + λ_j ∫‖P'''‖² dt

Кубический B-сплайн, открытые равномерные узлы через `knot_spacing_frames`. При фиксированных весах
остатки линейны по контрольным точкам: `A c − b`, где `A` — базис и его 2-я и 3-я производные в
точках квадратуры (трапеции). Решение — нормальные уравнения `(AᵀWA) c = AᵀW b` с IRLS-весами
Хьюбера `w_i ← w_i · min(1, h/‖r_i‖)` (6 итераций, ~1 мс). Для сравнения есть `solver = least_squares`
(scipy, аналитический якобиан, `max_nfev` адаптируется под `deadline_ms`).

Вывод: `latest(now)` — точка `now − lag_frames` (между обновлениями конец сплайна отстаёт на ≤
`update_every_frames`; запрос за концом продолжается по прямой со скоростью в конце — это прогноз,
не сглаженное измерение); `history()` — кадры, вышедшие из окна, заморожены по последнему сплайну,
их больше не пересчитывают. Производные дают сглаженные скорость и ускорение. Фоновый поток: очередь
из одного запроса (новый заменяет старый), результат под блокировкой; основной контур не ждёт.

Единицы: мир в см, время в кадрах; `λ_a = 10³`, `λ_j = 10⁵` подобраны на синтетике (10³/10⁴/10⁵ по
ошибке скорости и ускорения), на реальных данных стоит перепроверить.

## 7. Потоковый конвейер (`pipeline/streaming.py`)

- **Источники.** `VideoSource` (файл или URL/устройство, поток захвата; replay — ожидание исходного
  темпа от общего `t0`, метка `index / fps`; live — метка от часов захвата); `DetectionSource`
  (готовые детекции как кадры без изображения). Очередь `deque(maxlen = queue_size)`: новый кадр
  вытесняет старый (`dropped` считается); для файлов без темпа — режим без потерь (ожидание потребителя).
- **Синхронизация.** Опорная метка — минимальная из самых новых меток камер; кадры с
  `|t − t_ref| ≤ sync_tolerance_ms` входят в связку, остальные ждут следующего тика и помечаются
  исключёнными; кадры старше `max_frame_age_ms` отбрасываются. Если синхронизировать нельзя,
  триангуляция по таким кадрам не делается.
- **Детекция.** Пакет кадров выбранных камер одним вызовом `model.predict(list)` (ultralytics
  обрабатывает список как батч); `half` для FP16 на GPU; устройство — автоматически.
- **Метрики.** На каждом тике: время планировщика, детекции, фильтра, сплайна (в основном потоке),
  визуализации, тика; задержка кадр → оценка (`perf_counter` захвата → конец тика); FPS камер,
  изображений YOLO в секунду, выдача координат в секунду, активные камеры, пропуски очередей,
  исключения синхронизации, статусы, память (max RSS). `performance_report.{json,md}`.
- **Остановка.** Потоки захвата — daemon с событием остановки; сплайн — `wait_idle` + `close`;
  ffmpeg — закрытие stdin и ожидание.

## 8. Конфигурация (`pipeline/config.py`)

Разделы `cameras`, `streaming`, `detector`, `scheduler`, `triangulation`, `tracker`, `spline`,
`output`; JSON (`stream.py config` печатает полный), переопределения `--set раздел.ключ=значение`.
