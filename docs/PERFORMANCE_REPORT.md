# Отчёт о производительности (4 ноября 2026)

Машина: AMD Ryzen 5 4500U (6C/6T, AVX2, без CUDA), 7.4 ГБ ОЗУ, Windows 11 —
подробно в [HARDWARE_PROFILE.md](HARDWARE_PROFILE.md). Все числа — реальные замеры
на этой машине; фоновая загрузка CPU в момент замеров 30–40 % (десктоп), поэтому
у отдельных строк возможен шум ±20 %.

## Почему YOLO не успевала

- YOLO26s-seg @960, PyTorch CPU: ~0.25–0.28 с на изображение ≈ 3.5 изобр./с.
- 5 камер × 30 FPS = 150 изобр./с — в ~40 раз больше возможного.
- Детекция выполнялась синхронно в тике конвейера: тик длился секунды, очереди
  вытесняли 99.3 % кадров, трекер не успевал инициализироваться
  (замер `outputs/stream`: 5 тиков за 30 с, задержка p50 2.5 с).

## Замер бэкендов (tools/benchmark_hardware.py, batch 1–2, кадр 1920×1080)

| бэкенд | imgsz | мс/изобр. (batch 1 / 2) | изобр./с (лучший) |
|---|---|---|---|
| torch (PyTorch CPU) | 960 | 282 / 349 | 3.6 |
| torch | 640 | ~230 (шум) / 377 | 4.3 |
| torch | 480 | 133 / 106 | 9.4 |
| onnx (ONNX Runtime CPU) | 960 | 483 / 232 | 4.3 |
| onnx | 640 | 137 / 162 | 7.3 |
| onnx | 480 | 123 / 105 | 9.5 |
| **openvino** | 960 | 250 / 283 | 4.0 |
| **openvino** | **640** | **137 / 134** | **7.5** |
| **openvino** | **480** | **68 / 64** | **15.6** |

Авто-калибровка (`--auto-tune`, отдельный замер) выбрала **OpenVINO @640**
(108 мс/изобр. ≈ 9.2 изобр./с): в 2.5–3 раза быстрее исходного torch @960.
GPU-вариантов нет: ни CUDA, ни ROCm на Windows для Vega iGPU (512 МБ) недоступны;
OpenVINO видит iGPU, но для сегментационной модели на этой архитектуре выигрыша
не даёт и память критична (свободно < 1 ГБ).

Квантование INT8: на Zen 2 нет VNNI, ожидаемый выигрыш мал, а калибровка рискует
качеством — не применялось (зафиксировано как возможное направление).

## Выбранная конфигурация (configs/performance_profile.json)

- `detector.backend=openvino`, `detector.imgsz=640`, `detector.retina_masks=false`
  (центроид по полигону контура вместо маски полного разрешения);
- `streaming.max_images_per_tick=2` — бюджет YOLO на тик: стабильная стерео-пара,
  якорение камер, недавно находивших объект, разведка каждый 5-й тик;
- выбор размера: 480 ещё в 2 раза быстрее, но порог качества по умолчанию 640
  (`--min-imgsz`); проверка качества ниже.

## Реальное время (replay с исходным темпом, 5 камер, реальные видео)

| метрика | до (torch@960, без бюджета) | после (openvino@640, бюджет 2) |
|---|---|---|
| тиков/с | 0.16 | 2.46 (×15) |
| изображений YOLO/с | 0.20 | 4.85 (×24) |
| задержка p50 / p95, мс | 2542 / 15596 | 416 / 508 (×6 / ×30) |
| вытеснено кадров | 99.3 % | 83.3 % (обрабатывается 2.5 из 30 FPS) |
| статусы трекера | 100 % INITIALIZING (трек не начинался) | 69 MEASURED + 1 PARTIAL + 1 PREDICTED из 83 |
| первый measured-тик | никогда | кадр ~158 (5.3 с) |

Этому предшествовали три исправления реального времени (без них трекер не
инициализировался вовсе):
1. прогрев детектора до старта захвата (первая компиляция OpenVINO — 8 с);
2. бюджет выбирает стабильную стерео-пару (якорение нашедших камер), а не круговой обход;
3. окно буфера инициализации и предел коррекции положения фильтра масштабируются
   на фактический шаг тиков (раньше — константы «на кадр» при каждом кадре).

**Точность в реальном времени** (ошибка точки CSV, `tools/eval_stream_track.py`):
после первой итерации (openvino@640, бюджет 2) — медиана 5.8 м, p95 38 м: по 2 камеры
на тик при 2.5 тиках/с на резко маневрирующем грузовике (a_p90 = 8.8 м/с²) недостаточно.
Вторая итерация подняла частоту и геометрию, см. ниже.

## Вторая итерация: imgsz 480, бюджет 3, декодирование по требованию

1. Проверка качества @480 офлайн (детекции всех 5 видео, вариант A):
   **2.06 / 6.07 / 10.03 м** — не хуже 960 (1.99 / 6.12 / 8.96). 480 принят.
2. Декодирование по требованию (`streaming.decode_on_demand`, вкл. по умолчанию):
   при вытесняющих очередях `grab()` на каждом кадре, `retrieve()` (YUV→BGR + копия
   ~6 МБ) — только по выровненным индексам (все камеры декодируют одни и те же кадры,
   синхронизация не ломается: 1 исключение на 102 тика) либо при пустой очереди.
   За прогон пропущено ~3000 декодирований из ~5000.
3. Сравнение бюджета на реальных видео (openvino/onnx @480, RT replay):

| бюджет | тиков/с | ошибка мед / p95 / макс, м | статусы |
|---|---|---|---|
| 2 | 3.87 | 4.82 / 12.73 / 21.02 | 110 meas + 11 part + 4 pred |
| **3** | **3.02** | **3.02 / 6.20 / 7.78** | **96 meas, 0 pred** |
| 4 | 2.18 | 3.64 / 7.05 / 8.51 | 57 meas, 6 pred |

   Три камеры в тике дают заметно лучшую геометрию, чем две; четыре — уже не окупают
   падение частоты. Правило в auto-tune: ≥10 изобр./с — бюджет 3, иначе 2.

**Итог второй итерации** (профиль: openvino@480, бюджет 3, RT replay всего ролика):
102 тика (3.0/с), 9.1 изобр./с YOLO, задержка p50 354 / p95 528 / макс 685 мс,
96/102 MEASURED (0 PREDICTED), инициализация за 1.8 с; ошибка точки CSV —
**медиана 3.02, p95 6.20, макс 7.78 м**: p95 и максимум на уровне офлайн-качества,
медиана на 1 м хуже офлайна (3.0 против 2.0) — честная цена реального времени на
этом CPU. Пути дальнейшего улучшения: GPU; выделенная машина без фоновой нагрузки.

## Качество 3D-траектории (detections-режим, все 1001 кадр, вариант A, реальные данные)

| метрика | детекции @960 (baseline) | детекции openvino@640 |
|---|---|---|
| ошибка точки CSV: медиана / p95 / макс, м | 1.99 / 6.12 / 8.96 | 2.04 / 5.98 / 9.80 |
| ошибка скорости: медиана / p95, м/с | 1.04 / 8.24 | 1.06 / 8.27 |
| доступность оценки | 98.5 % | 98.4 % |
| PREDICTED-кадров / потерь трека | 0 / 0 | 0 / 0 |

Число кадров с детекцией почти не изменилось (cam1 198→197, cam2 494→491, cam3 413→413,
cam4 452→414, cam5 765→767): заметно потерял только cam4 (−8 %), на итоговые метрики
это не повлияло. Переход 960→640 + retina_masks=false **не ухудшает качество** — медиана
+0.05 м, p95 даже лучше. Размер 480 быстрее ещё в 2 раза, но без такой же проверки
качества по умолчанию не используется (`--min-imgsz 480`, затем `stream.py variants`).

Оговорки (как и раньше): YOLO дообучена на этих же видео — оценка на обучающих
данных; точка CSV и пределы ускорения подобраны по CSV цели.

## Ограничения

- 150 изобр./с на этом CPU недостижимы ни одним бэкендом (лучшее ~15.6 изобр./с
  @480). Система работает адаптивно: бюджет изображений + планировщик камер,
  трекер выдаёт оценку на каждом тике (между детекциями — прогноз).
- Замеры производительности на ноутбуке зависят от фоновой нагрузки и троттлинга.
- OpenVINO-экспорт кэшируется в `models/best_openvino_model/` (в git не попадает).
